# Database contract

**Status:** Normative logical design, revised October 16, 2026. Shared Drizzle/SQLite schema for the initial React SPA (SQLite WASM/OPFS worker binding) and subsequent React Native/Expo application (expo-sqlite). The first-turn subset is implemented and migrated against real Node SQLite and browser OPFS; the full logical design below remains the target contract. No published-upgrade/native qualification is implied. Read with [architecture sections 3–9](../../ARCHITECTURE.md).

## Types and field notation

Every field below is required and non-null unless suffixed `?`. No implicit defaults apply. `Id` is opaque UTF-8 text, generated once and never reused; source/content IDs are stable authored text. `Hash` is lowercase 64-character SHA-256 hex. `N` is a nonnegative signed 64-bit integer (application JSON represents it as a decimal string outside the interoperable safe-integer range); `V` is a positive schema/codec integer. `Bool` has only true/false. `Bytes` is a byte string. `Json<T>` is a size-bounded, versioned, strictly validated payload of the named type, not arbitrary application state. Enums list all permitted values. Wall-clock timestamps are optional diagnostics, never ordering or ownership authorities, and are not stored in this initial schema.

`PK` defines the primary key. `UQ` defines a unique key. A child foreign key referencing an ownership tuple must match **every** tuple field. An ordinary independent profile FK does not replace it. Package membership and typed JSON invariants are validated by the transactional writer as specified below.

## Ownership, cardinality, indexes, and deletion

The writer enforces these relationships with composite SQL FKs where possible and transactional validators for bounded JSON references:

1. Every personal `(profile_id, generation)` matches its exact profile tuple. A run references its session's owner/course/package/lesson tuple. Historical runs may differ from the session's current task.
2. `session.current_run_id` matches the full run tuple including current task. A session has exactly one current run and may retain older runs. `profile.undo_run_id` matches that owner/generation, independently of course. An active/paused writable session's current run is inProgress. A terminal closed session remains valid for the current Undo window.
3. Documents, advances and task credits match their run's exact ownership. Terminal credits additionally reference a terminal accepted advance of that run. Result rows reference valid credits of the exact owner/course/task or lesson. Cross-profile/release links are invalid even when individual IDs exist.
4. A run's active advance is null or the accepted head of its own acyclic increasing-sequence chain. Previous links stay within that run. Withdrawn rows cannot contribute acceptance or be an active head. There is one valid terminal task credit at most per run. Lesson support is an exact set of same-owner valid task-credit IDs, matching receipt hashes and the pinned package's accepted task set.
5. Package references retain immutable metadata. Every retained run, including terminal runs supporting historical credits, pins the exact required runtime bytes for import/migration membership validation. Current Undo state and retained drawings also pin those bytes. Closing a run or deleting only drawings does not remove its package pin. Strokes/history belong to documents, chunks to strokes and operations to their document/layer's strokes.
6. At most one active session exists per owner/course and one active-or-paused session per owner/course/scope-kind/scope-target. Closed sessions do not occupy these slots. Progression/lessonReplay targets are lessons; taskReplay targets are tasks.
7. The course resume pointer matches its owner/course and an active/paused session, or its closed terminal session while that run owns the profile Undo window. Selection uses the unique cursor counter, never wall-clock time. Return-session hints use the same owner/course and never self-reference.

Run status normally moves inProgress to completed/skipped/abandoned. Undo is the sole terminal-to-inProgress exception and requires the open profile window plus terminal advance reversal. Finishing commits the terminal current run and completion view without creating another run. Explicit next-task Start creates/assigns its run and replaces the profile undo pointer atomically. Explicit Restart abandons unfinished work and allocates a new run. Pausing/restart recovery, Back, map navigation and avatar changes do not allocate runs or close Undo.

Required indexes include PK/UQ keys, both live-session cardinality indexes, owner/course/status/selection sequence, run session/ordinal, advance run/sequence/status, task credit owner/course/task/status and terminal identity, lesson credit owner/course/lesson/status and package, result owner/course/lesson, documents owner/package, stroke document/layer/order/status, chunk stroke/index, operation document/layer/sequence/origin, receipt owner/generation and scope/revision, and package references. Credit selection first determines the highest valid outcome, completed before skipped. Retain the existing selected credit when it is still valid at that outcome. Otherwise select the lexicographically smallest valid credit ID at the highest outcome. Lesson result retains its existing valid selected credit, otherwise selects the smallest valid lesson-credit ID. The order is deterministic and has no timestamp dependency.

Reset retains profile identity/preferences, increments generation/revision, clears its undo pointer and all prior-generation work/cursors atomically. Delete removes the profile and owned graph; recreating allocates a new ID. These operations remove task/lesson projections, credits/support, advances, personal receipts, sessions/runs, documents/chunks/history/previews and pending jobs. Shared content never cascades from personal deletion. Result/current-run/undo links use deferred NO ACTION constraints so the complete graph must be valid at commit. Return hints are nulled when their target is removed. Installation delete receipts are redacted and contain no removed owner IDs.

Ordinary history cleanup cannot remove a run's open Undo chain or valid credits/support. After its Undo window closes, retain the small run/terminal acceptance metadata and receipt support needed by valid credits. Parent-selected removal of older drawing bytes does not remove valid task credit; content needed by remaining saved context stays pinned. Closing a session is archival. Removing any referenced run/credit fails unless all references are explicitly handled in the same transaction.

## Transaction and identity protocols

**Create/start/replay.** Allocate a new session/run, validate membership, and assign the full `current_run_id` tuple in one transaction. Circular references are deferred; no placeholder state escapes. Starting any new run replaces `profile.undo_run_id`, closes the prior window, updates affected course resume pointers if they held a now-nonundoable terminal session, and retains earlier valid credit. Resuming an existing run never resets state. A superseded paused delivery can resume its saved context and accept new teaching, but cannot regain its closed Undo window. Only the last newly started run for that child can expose Undo. The parent UI disables or omits Undo when this run is not the profile pointer or its active advance is null. No automatic next-run creation hides a terminal Undo opportunity.

**Accept.** Close/finalize/flush ink under the input fence first. In one transaction recheck ownership, session/run identity, expected revisions and committed document revision. Evaluate source obligations, append the next `task_advance` snapshot and active-head link, update run/state/phase/input epochs, and create a terminal `task_credit` when eligible. Derive task and lesson results from valid credits and insert a supported lesson credit if the currently accepted task set is fully satisfied without an existing valid equivalent support. Persist cursor and command receipt before publishing. Reconfirming an already accepted occurrence after Back changes navigation/revision only and cannot duplicate a cycle, advance or credit.

**Undo advance.** Validate that this is the profile's current undo run and the requested latest accepted head. Fence/flush ink. Restore the head's before-state, mark it withdrawn, move the active head to its prior accepted row, and withdraw its terminal task credit if any. Withdraw every lesson credit directly supported by that now-invalid task credit, then recompute effective results from all remaining valid credits. A newly valid alternative full support can create a new lesson credit in this same transaction. Undo of a just-completed task reopens its session/run and course cursor; conflicting live scope slots are paused/closed consistently before commit. Retain all canonical ink/history and bump input epochs when phase permission changes. Receipt and all revisions commit together. Restart restores this exact open chain, including terminal state. Repeated Undo stops at null head. New acceptance allocates a fresh sequence; withdrawn records never count as Redo.

**Command envelope:** every mutation carries scope kind/ID/generation, command ID, expected scope revision, profile ID/generation where personal, and SHA-256 of canonical command kind plus payload (including target IDs). Ink callbacks additionally carry document/run ID, phase, input epoch, stroke ID, and sample/chunk sequence. On each write compare generation and the current ownership graph **inside** the transaction, including queued writes. A writer assigns the next expected document revision only after earlier queued edits commit; callbacks cannot guess new revisions. Reset/delete closes input first, cancels effects and queued work, then invalidates ownership. A late callback cannot recreate missing parents.

Same receipt key/same payload returns the saved result without executing again. Same key/different hash is a command-identity error, including after a screen change. Receipts are checked only after scope ownership/generation is validated. A retry without a retained receipt must satisfy the original expected revision; every accepted command, including accepted no-ops, increments its scope revision. Pruning therefore cannot turn an old retry into a fresh mutation.

Profile creation/reset/deletion and session creation use installation/profile administrative scope as applicable, with expected installation/profile revision rather than a nonexistent session revision. Installation scope serializes profile creation/deletion; reset is profile-scoped and stores its receipt under the resulting generation. A retry carrying the old generation is rejected as stale, with the coordinator reading the new committed state; it is never executed again. Successful deletion increments installation revision before its redacted receipt is exposed. Receipt retention: newest 256 per live personal scope, purge with its owner, newest 256 installation receipts. Valid task/lesson credits and the open Undo chain are retained separately.

**Credit and projection.** Only parent acceptance of authored obligations creates completed credit. Optional writing Skip creates skipped credit. Both are reversible only while their run owns the open Undo window. Effective precedence is completed over skipped over absent among valid credits. An unfinished replay contributes nothing. Undo of a current completed replay leaves earlier valid completed credit intact; undo of the first completion removes the effective result if no earlier valid credit exists. Undo of completed following an earlier valid skip returns the projection to skipped. A malformed completed credit cannot be used to bypass an obligation.

Lesson credit stores its accepted task-set snapshot and exact supporting task-credit identities. New editorial tasks never invalidate a historical valid snapshot or invent credit for the additions. Undo withdraws dependent support credit only; unrelated earlier lesson credit remains. These records drive truthful map/progress/recommendation views. They never lock available curriculum. Any installed compatible task can start through explicit parent override; unseen work stays incomplete. Content mappings for unfinished work must preserve instructional identity rather than infer it from order.

**Content membership:** ContentRepository validates task/lesson/node/item/target IDs, review selections, graph checkpoints, and source refs against the exact verified package. The writer rechecks immutable package identity and ownership before commit. SQL cannot FK directly into package JSON; this validation is mandatory for both SQLite bindings. Imported/migrated state uses the same validators before becoming visible. Neither Drizzle types nor React Query cache validation replaces these checks.

## Stroke chunks, recovery, and undo

Chunks append in index order starting at zero; `first_point_index` equals the sum of previous chunk counts. Each chunk contains at most 2,048 points. A checkpoint transaction writes complete chunks, updates stroke point count, document revision and receipt, leaving status capturing. The final short chunk is immutable once committed; subsequent samples start a new chunk. Duplicate checkpoint keys return the receipt; a chunk-key collision with different bytes is rejected. Neither checkpointing nor chunk boundaries create extra AddStroke edits.

End/cancel transaction appends remaining confirmed points, changes status to finished/interrupted, and appends exactly one AddStroke operation. Its unique origin ID prevents duplicate history insertion. An empty capture is removed without an operation. On startup, with input still closed, a recovery transaction finds capturing strokes, validates/trims only an uncommitted tail (committed chunks are never silently discarded), marks each nonempty stroke interrupted, inserts its missing AddStroke, and advances history/document revision. Re-running recovery finds no capturing stroke and creates no second operation. The pointer never resumes. A malformed committed chunk produces a recoverable corruption state, not truncation disguised as success.

History is per layer. Evaluate visibility from its baseline through operations up to cursor. Undo moves cursor to the previous retained sequence or base; Redo moves it to the next retained sequence. Sequence IDs are monotonic and may have gaps. Model, tracing and independent layers each have their own baseline/cursor/history; an earlier phase cannot undo later-phase ink. New editing after Undo deletes the redo suffix transactionally before allocating `next_op_seq`; it collects only strokes unreferenced by baseline, retained operations, or live capture. Clear changes visibility and retains bytes needed by Undo. It does not promise to free disk space.

Retain up to 128 operations per layer. Before another append, compact the oldest applied prefix into a new visible-stroke baseline and delete that prefix atomically; advance base, preserve cursor/tip, and collect only now-unreferenced finalized strokes. Do not compact an unapplied redo prefix. Discard redo first on a new edit. A finalized stroke already folded into baseline needs no reconstructed AddStroke on restart; only capturing strokes go through recovery. Undo cannot cross baseline. The parent UI exposes that availability, with app-origin highlighting.

Proposed engineering bounds: 100,000 points/stroke; 1,000,000 retained points or 32 MiB canonical data/document, whichever first; 4 MiB live renderer buffer and 2 MiB uncommitted write queue. At a bound, finalize the confirmed partial stroke and fence input; flush or offer a parent recovery action before accepting more. Never drop old committed points or claim a truncated gesture is complete. These are implementation budgets to validate on minimum devices, not counts of letters or teaching criteria. Warn the parent at 250 MiB total personal data; offer parent-selected deletion of older drawings/replays, without removing task outcomes. No automatic personal-work expiry. Disposable previews/packages not pinned for use may be collected first. Neither reversible Clear nor Undo is a disk-full remedy.

## Drizzle, binding parity, and migration

SQLite: explicitly enable and read back `PRAGMA foreign_keys=ON` on **every connection before transactions**. Use composite unique parent keys, matching composite FKs, deferred circular links, CHECK constraints for enum/range/null rules, partial unique session/capture indexes, and transactional validators for JSON/graph/history rules. Pin a SQLite feature floor for the generated DDL on both bindings. The [SQLite documentation](https://www.sqlite.org/foreignkeys.html) explains connection-specific FK enforcement. Native WAL/FULL and browser rollback-journal/FULL settings follow architecture §8.2–8.3 and must be verified on the actual drivers.

Drizzle schema/query definitions and generated SQL migrations live in the shared storage package. Review generated SQL; add required raw SQL for deferred composite relationships, partial indexes, and constraints not represented by its schema DSL. Package one ordered migration set for both drivers. Drizzle Kit generates files, while the checksummed transactional runner remains the sole migration authority; do not independently apply Drizzle's default migrator and the application's ledger. Verify the schema/constraints after each migration, not only TypeScript compilation. The existing logical records remain the specification for that schema.

SPA: Drizzle's SQLite-proxy adapter sends parameterized SQL to a dedicated SQLite WASM/OPFS worker. It is a local message bridge, not a server. Keep whole transactions serialized: BEGIN, validator reads, all affected writes, COMMIT/ROLLBACK form one exclusive unit. Route query-cache reads through the same scheduler so they cannot observe a transaction before commit. Worker responses preserve row/value ordering and canonical BLOB bytes. Resolve the store receipt only after durable COMMIT acknowledgment; worker loss rejects the pending operation and recovery reads the last committed state. Hold origin/database ownership before opening, with a clear second-tab recovery state. There is no IndexedDB personal-record fallback.

Expo: inject the expo-sqlite Drizzle driver behind the same async repository/store ports. Respect its pinned driver's transaction API: synchronous callbacks stay synchronous, and unrelated async work cannot enter an open transaction. Serialize all access through the writer/read scheduler; screens and React Query do not receive an unrestricted DB handle. Saving batches must not block the native ink render/input path. Validate BLOB/enum/large-integer encoding equivalence with the web executor.

Both bindings transactionally validate the same prospective ownership graph and package membership. Session acceptance/Undo touches profile/undo pointer, package metadata, cursor, sessions, runs/advances, task/lesson credits and their projections, affected ink document/phase/history, and receipts. Stroke transactions validate profile/session/run ownership while updating document, stroke/chunks, history/operations, and receipt. Reset/delete spans all owned personal rows plus administrative scope as needed. A preflight-only ownership check or successful ORM statement is insufficient. Parent reset invalidates query keys/results as well as DB generations.

Migration checks old version and checksum, validates the transformed graph, writes data plus migration row plus database version in the same transaction, then opens normal access. A failed migration leaves the last committed database intact. A newer unsupported DB opens only a recovery/update screen; never create a replacement empty DB. Nontransactional future migrations need a separately reviewed journal/recovery protocol. Test from every published DB version and keep its fixture. The initial development schema migration has run against real SQLite and browser OPFS. Published-version upgrades and the native binding remain unqualified.

Shared migrations do not move a browser sandbox's database into a native sandbox. Migration tests load the same controlled state fixtures in both executors. The required protected complete backup/restore feature supplies deliberate cross-binding transfer after its interoperability checks pass. Installing Expo alone does not transfer browser data.

## Complete backup and new ownership

Export reads one consistent committed snapshot after selected profiles' ink is flushed and input fenced. The profile graph includes preferences/avatar IDs, course cursors, sessions/runs, profile Undo pointers, complete open advance chains, task/lesson credits and exact support, result projections, canonical stroke chunks and edit histories, state/codec versions, and exact runtime package/asset closure needed for offline resume and membership validation of every exported run/credit, including completed/skipped runs without drawings or an open Undo window. Exclude original PDFs/scans/transcriptions, authoring paths, secrets, logs, renderer caches and the old installation identity. Package/asset hashes and signatures verify the runtime closure, not just references to future downloads.

The parent-gated archive is passphrase-protected authenticated ciphertext using STACK's qualified versioned format and resource bounds. No passphrase or key is stored in SQLite. Export succeeds only after real file write and archive verification. No account-based recovery exists. Temporary plaintext staging is app-controlled and cleaned on every exit path.

Restore authenticates and validates into staging before touching personal data. Reject wrong passphrases, malformed ownership/advance/credit/ink graphs, unknown mandatory schemas, excessive sizes, content hash/signature mismatch or missing required runtime bytes. Preview permits rename and Cancel. Names never select existing records. Every restored profile gets a fresh ID and ownership generation. Domain revisions and accepted-revision relationships are preserved; old executable command receipts are excluded. Allocate fresh personal run/session/advance/credit/document/stroke/command IDs and remap all foreign keys, undo/return/resume pointers, support references, history payloads and baseline stroke sets. Keep authored source/target IDs, package hashes and canonical geometry unchanged. Rebuild affected receipt hashes while preserving original acceptance hashes as import provenance. Old command retry identities are not active in the new ownership scope.

After inactive runtime publication is verified, one installation-scoped import transaction inserts all selected complete new profile graphs, validates derived projections and records a stable import-operation receipt. Before commit, no new profile is visible. Failure leaves existing profiles and active selection untouched. Retry of the same operation returns its original new profile IDs; a separate deliberate reimport creates new profiles after preview. Unreferenced staged content is collected separately. Existing live input is fenced for administrative commit, then resumes without ownership reassignment. Acceptance requires offline reopening of each restored context and cross-binding round trips, including current-run terminal Undo, previous valid credit and editable canonical ink.
