# SQLite browser compatibility

Issue #2 selects `@sqlite.org/sqlite-wasm` 3.53.4-build2, SQLite's official ES-module distribution, for one worker-owned `opfs-sahpool` connection. The wrapper has Apache-2.0 notices; SQLite core is public domain. Exact locked artifacts and bundled notices remain release inputs.

Inspection of this artifact found that `installOpfsSAHPoolVfs` calls `removeVfs` after initialization failure. That cleanup recursively deletes its managed directory. A failed open must preserve existing personal data, so the build replaces that cleanup with access-handle release and rethrow. The checked transform also separates handle acquisition from metadata interpretation. It waits for every acquisition outcome before processing any header, and closes every successful handle before rejecting an acquisition failure. Native acquisition completion order and the original successful return shape are retained. The pinned SQLite/WASM binary is unchanged.

The build transform checks the original artifact's SHA-256 and requires the cleanup occurrence exactly once. A dependency change fails the build until reviewed. No dependency installation is silently rewritten. Both Vite development and production worker builds must use this transform. The real-browser qualification must seed saved teaching, force initialization failure through an actual held OPFS file handle, release it, reopen and verify saved state and bytes. A string comparison alone does not establish preservation.

Upstream's [current persistence documentation](https://sqlite.org/wasm/doc/trunk/persistence.md#vfs-opfs-sahpool) describes a `preserveOnInitFailure` option added in SQLite 3.54. The pinned 3.53.4 artifact lacks that option. A future supported release can replace the local transform after the same restart/failure suite passes. The initial issue-02 held-file qualification passed in both Vite development and built production workers. Issue-14 CI later exposed an acquisition-ordering case that the cleanup-only change did not cover. Full browser-process restart, competing-tab ownership and lost-COMMIT-reply recovery pass too. Qualification currently covers headless Chromium 156 on the development host; it does not establish supported tablet hardware, Safari, native SQLite or the complete application matrix. See [the evidence record](../evidence/issue-02.md).

## Failed acquisition preservation

[Issue-14 CI run 39080150783](https://github.com/hyetigran/read-at-three/actions/runs/39080150783) changes one pool-file hash during a held-handle initialization failure. The trace does not retain its original file bytes, so its exact originating interruption remains unproven. Ten unchanged local repetitions pass and do not dismiss the failed run.

The pinned initializer processes each acquired handle immediately. Its metadata reader can truncate an unused file before a different acquisition rejects. A pending successful acquisition can also finish after failure cleanup and retain a native handle. Real-browser diagnostic cases reproduce both mechanisms using a deliberately seeded residual tail on an otherwise valid unused slot and a separate genuinely held native file. This synthetic residue is distinct from the unavailable original CI image.

The transform now waits for all parallel acquisitions to settle before any metadata interpretation. Failed acquisition closes all fulfilled handles and propagates the native error without reading, clearing or truncating a pool header. Successful acquisition retains the existing interpretation order and result shape. Both the dependency checksum and exact original-method occurrence are guarded. Unexpected source fails the build rather than applying a guessed patch.

Two public native-OPFS regressions control acquisition order through native completion/rejection barriers. They compare every complete seeded file by name, length and SHA-256, prove every handle is reacquirable while the failed worker remains alive, and reopen the saved child-response turn. Both fail on the cleanup-only build and pass on the corrected build. The original held-file test remains unchanged. These focused cases pass in development and built production. Full current-head qualification and CI are recorded with the issue-14 delivery evidence. This change does not claim filesystem rollback for arbitrary failures after successful handle acquisition.

## Database upgrade compatibility

Issue #3 adds task credits and effective task results through database version 2. The ordered migration ledger retains the exact version-1 statements and checksum. Startup verifies the installed ledger, schema and ownership graph before applying a newer migration. Each migration commits its DDL, installation version, checksum row and SQLite user version atomically. A failed upgrade keeps the previous schema and saved records.

The upgrade test loads a synthetic database captured from the merged issue-02 application at its child-response turn. It verifies unchanged owned state and package BLOBs, then resumes through the legacy decoder. Full-task content becomes the active bundled development catalog without rewriting that saved run. An explicit parent action creates the new full task. Startup never replaces a later active catalog with an earlier bundle. General package installation and update remain separate delivery tickets.

Issue #4 adds database version 3 with a nullable `task_advance.accepting_command` JSON column. The version-1 and version-2 statements/checksums remain unchanged. Newly accepted commands store their canonical kind/payload hash preimage with the before/after snapshots. Reopen verifies the exact action, target and acceptance delta even after retry receipts are pruned. Existing legacy/printed rows with NULL retain their original Continue semantics. Control-state acceptances require explicit saved semantics. A genuine version-2 database captured from merged `58a7725` verifies exact pinned correction recovery, each migration write failure, rollback, retry and uncertain COMMIT acknowledgment.
